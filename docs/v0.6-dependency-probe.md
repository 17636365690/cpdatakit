# v0.6 dependency probe

This report records the first local dependency probe for the v0.6 preflight. The probe is a
diagnostic artifact, not a runtime lock file. Runtime dependencies will enter `pyproject.toml` only
after the same candidate set passes the supported operating-system matrix.

## Candidate set

The candidate constraints live in `scripts/v06-dependency-candidates.json`. The common baseline is
Python 3.12, NumPy 2.x, pandas 2.2+, xarray 2026.7+, Zarr 3.1+, PyArrow 25.x, and explicit FastAPI
web dependencies. `h5py` is included because h5netcdf uses it as its HDF5 backend.

The selection follows the upstream requirements consulted on 2026-09-02:

- [xarray installation](https://docs.xarray.dev/en/stable/installing.html)
- [Zarr installation](https://zarr.readthedocs.io/en/latest/user-guide/installation/)
- [Apache Arrow Python installation](https://arrow.apache.org/docs/python/install.html)
- [FastAPI on PyPI](https://pypi.org/project/fastapi/)

## Operations

The same environment performed these real operations with a deterministic dataset containing
`temperature(time=4,y=3,x=4)`:

- xarray wrote and reloaded NetCDF through h5netcdf. Output size was 8,728 bytes.
- xarray wrote and reopened a Zarr format 3 store. The store contained 23 entries.
- PyArrow wrote and reloaded a four-row Parquet table. Output size was 1,803 bytes.
- FastAPI and HTTPX served and called a local `/health` route.

All operations returned the expected shapes or rows. No network request was needed after package
installation.

## Cross-platform matrix probes

The repository now includes `.github/workflows/v06-dependency-matrix.yml`. Each matrix cell creates
an isolated environment, installs the selected candidate set with `--only-binary=:all:`, installs
CPDataKit editable for source validation, runs the five smoke operations above, and uploads a JSON
report. The workflow covers Ubuntu, macOS, and Windows with Python 3.12 and 3.13 for both `lower`
and `latest` candidate sets.

The locally available cells were also run directly:

| Operating system | Python | Candidate set | Wheel-only candidates | Smoke operations |
| --- | ---: | --- | --- | --- |
| Windows | 3.12.10 | lower | pass | 5/5 pass |
| Windows | 3.12.10 | latest | pass | 5/5 pass |
| Linux (WSL) | 3.13.15 | lower | pass | 5/5 pass |
| Linux (WSL) | 3.13.15 | latest | pass | 5/5 pass |

Cross-target pip wheel resolution also passed for the macOS direct candidates on both architectures:
arm64 used a macOS 14 target for Python 3.12/3.13 and x86_64 used a macOS 13 target for Python
3.12/3.13, with both `lower` and `latest` constraints. This confirms selectable wheels but does not
replace importing and running the operations on macOS. The hosted macOS cells and the remaining
Python 3.12/3.13 runtime cells are intentionally left to workflow runners; this Windows host cannot
execute macOS. A candidate set is not promoted to runtime metadata until its required hosted cells
pass.

## Findings and follow-up

The first NetCDF attempt failed because h5netcdf was installed without h5py. The candidate manifest
now lists h5py explicitly. A later cross-platform probe must confirm whether h5netcdf alone can cover
the desired NetCDF4 subset and whether netCDF4 is worth its larger native footprint.

Starlette emitted a deprecation warning for its synchronous TestClient with HTTPX 0.28.1 and pointed
to `httpx2`. v0.6 UI tests should use an ASGI transport or the supported HTTPX test path once the
upstream compatibility package is stable. The warning does not affect the route result.

Zarr emitted a warning that consolidated metadata is not part of the Zarr format 3 specification.
The v0.6 writer must avoid assuming consolidated metadata for Zarr 3 and must test interoperability
with an independent reader.

The current CPDataKit v0.5 environment contains NumPy 2.5.2 and pandas 3.0.5 but none of the new
format or UI packages. This is expected. The candidate environment is isolated under a temporary
directory and is not part of the project distribution.

## Next probe gate

Before changing runtime metadata, wait for the hosted macOS matrix cells, inspect licenses across the
uploaded reports, and measure a cold import of CPDataKit plus the future `cpdatakit ui` entry point.
The runner records the exact resolved versions for the lower-bound ranges rather than silently
claiming that a range's newest patch is the literal lower patch. Record failures as capability-
specific diagnostics instead of silently dropping a format.
