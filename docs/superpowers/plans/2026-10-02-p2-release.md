# P2 repair and v0.10.1 release plan

**Goal:** Complete audit R04–R09 with the accepted P1 fixes, verify the combined product, then publish v0.10.1 through the existing protected GitHub/PyPI workflow.

**Architecture:** Request budgets and instance sessions are handled before upload parsing; immutable parent provenance is carried by writers; HDF5 metadata limits precede payload reads and report services reuse loaded data; NetCDF4 backend access supports Windows Unicode paths without changing source files. PyPI documentation uses release-pinned absolute links.

**Tech stack:** Existing Python 3.12+, FastAPI/Starlette, NumPy/pandas/Pint, h5py/xarray/netCDF4, hatchling, pytest, GitHub Actions OIDC. No new external service or runtime dependency.

**Spec:** User-approved P2 completion and publication, based on the 2026-10-02 audit R04–R09 and proposals F3–F8. Correct adjacent capability/roadmap statements as part of release documentation. New recipes, batch UI, row lineage, adapters and training features are excluded.

## Constraints

- Preserve prior P1 changes and sibling worktrees. Base main is f26a97584e6dc8eee415580847a7281ce76c7508.
- Use synthetic inputs, bounded tests and red/green logs under ignored `.artifacts/p2-release/`.
- Publication is authorized: commit reviewed files, open PR, complete required CI, merge, push semantic tag, verify PyPI, then create matching GitHub Release. Never bypass branch/deployment protections or copy credentials.
- PyPI artifacts are immutable: do not tag before the final source/metadata/tests pass. Keep runtime version, citation, changelog, docs and release notes aligned.
